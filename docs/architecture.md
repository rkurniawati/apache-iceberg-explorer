# Architecture & Execution Model

This document outlines the architecture, runtime environments, and communication patterns of the **Iceberg Explorer** VS Code extension.

---

## 1. High-Level Execution Model

VS Code extensions run in a multi-process model. In this extension, code is split across two distinct environments:

1. **Node.js (Extension Host Process)**:
   - Handles the extension lifecycle, filesystem I/O, network requests, credentials, background workers, and VS Code API integration.
   - Heavy query processing (DuckDB-WASM and Avro decoding) runs here.
2. **Chromium (Webview Sandbox Processes)**:
   - Each webview panel runs in an isolated browser iframe/process rendered by Chromium.
   - Responsible strictly for rendering HTML/CSS, capturing user interactions, and updating the client-side DOM.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        NODE.JS (Extension Host)                        │
│                                                                        │
│  extension.ts                                                          │
│   ├── connection/    SecretStorage & Connection configs                │
│   ├── storage/       LocalFs, S3, & GCS (@google-cloud/storage)        │
│   ├── tree/          VS Code Sidebar TreeDataProvider                  │
│   ├── query/         DuckDB-WASM (node:worker_threads) & Avro (avsc)   │
│   └── panels/        WebviewPanelManager & WebviewReadyGate            │
│         │                                                              │
└─────────┼───────────────────────▲──────────────────────────────────────┘
          │ panel.webview         │ vscode.postMessage()
          │   .postMessage()      │ (WebviewMessage)
          │ (PanelMessage)        │
┌─────────▼───────────────────────┴──────────────────────────────────────┐
│                    CHROMIUM (Webview Sandbox Panels)                   │
│                                                                        │
│  Generated by src/panels/html/*.ts:                                    │
│   ├── Client DOM & UI components (buttons, tabs, inputs, breadcrumbs)  │
│   ├── Interactive renderers (SVG DAGs, tables, JSON trees)             │
│   ├── Client state & pagination (tableOverview, metadataStructure, query) │
│   └── acquireVsCodeApi() message dispatch                              │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Node.js Components (Extension Host)

All backend logic, storage adapters, heavy computation, and VS Code API hooks run in Node.js.

### Extension Lifecycle & Commands (`src/extension.ts`)
- Manages `activate()` and `deactivate()`.
- Creates and shares the single extension output channel logger (`ILogger`).
- Instantiates core singletons (`ConnectionManager`, `LocalFsAdapter`, `S3Adapter`, `GcsAdapter`, `QueryEngine`, `WebviewPanelManager`).
- Wires up the sidebar `vscode.window.createTreeView`.
- Registers VS Code commands (`icebergExplorer.openSettings`, `icebergExplorer.openTableOverview`, etc.).

### Connection & Credentials (`src/connection/`)
- **`ConnectionManager`**:
  - Persists non-secret connection configurations to `vscode.ExtensionContext.globalState`.
  - Securely stores sensitive AWS credentials (`accessKeyId`, `secretAccessKey`, `sessionToken`) and GCS Service Account Keys in `vscode.SecretStorage`.
  - Seamlessly supports Google Cloud Application Default Credentials (ADC) without requiring stored secrets.
- Handles active connection switching and schema validation.

### Storage Adapters (`src/storage/`)
- **`StorageAdapter`** interface: Abstracts reading metadata files and directories across different backends.
- **`LocalFsAdapter`**: Uses `node:fs` and `node:fs/promises` to read Iceberg tables from the local disk.
- **`S3Adapter`**: Uses `@aws-sdk/client-s3` to query metadata and data files from AWS S3, MinIO, or custom S3-compatible object storage endpoints.
- **`GcsAdapter`**: Uses `@google-cloud/storage` to query Iceberg tables stored in Google Cloud Storage (`gs://` or `gcs://`), supporting both ADC (zero config) and Service Account Keys (raw JSON or key file path).
- Standardizes errors (`access-denied`, `not-found`, `parse-failure`, `internal`) across storage providers.

### Sidebar Tree View (`src/tree/`)
- **`IcebergTreeProvider`**: Implements `vscode.TreeDataProvider` to render the tree in the VS Code Activity Bar:
  - Saved Connections $\to$ Namespaces/Databases $\to$ Tables $\to$ Snapshots / Metadata versions.
- **`commands.ts`**: Implements contextual actions on tree items (activate, edit, delete, open overview).

### Query Engine (`src/query/`)
- **`QueryEngine`**: Executes SQL queries over Parquet data files using `@duckdb/duckdb-wasm` inside a Node worker thread.
- **Avro Manifest Decoder**: Uses `avsc` with custom native `BigInt` unpackers to read binary Iceberg manifest lists (`.avro`) and manifest files.
- **`sqlAnalyzer.ts`**: Uses `pgsql-ast-parser` to parse and validate user queries, enforce row limits, and detect simple table scans for optimization.

### Webview Host Manager (`src/panels/webviewPanelManager.ts`)
- Manages the lifecycle of all open webview panels (`vscode.WebviewPanel`).
- Enforces singleton panel rules per resource (focusing existing panels instead of duplicating them).
- Implements `WebviewReadyGate` to buffer outbound messages until the webview frontend finishes initializing.

## 3. Chromium Components (Webview Sandboxes)

The files in `src/panels/html/` are TypeScript modules that run in Node.js to **generate HTML strings**. However, the CSS styles and JavaScript embedded within `<script>` tags are loaded and executed inside **Chromium**.

### Client-Side Execution Context
- **VS Code API Access**:
  ```javascript
  const vscode = acquireVsCodeApi();
  ```
- **Lifecycle & Ready Signal**:
  Every panel immediately posts `{ type: 'webviewReady' }` as its very first action to notify the host that listeners are active.
- **Message Handling**:
  Listens for host events via `window.addEventListener('message', (event) => { const msg = event.data; ... })`.

### Shared Scripts (`src/panels/html/shared.ts`)
- `SET_STATE_SCRIPT`: Handles `setState` messages to switch between loading spinners, error alerts, and content views.
- `RENDER_TABLE_SCRIPT`: Dynamically builds table DOM nodes (`<th>`, `<td>`) from query results.
- `ESC_SCRIPT`: Client-side string escaping for safe DOM manipulation.

### Webview Panels
| Panel HTML Generator | Runtime in Chromium |
| :--- | :--- |
| **`tableOverview.ts`** | Tab navigation (Schema, Snapshots, Partitions, Preview), live column search, snapshot pagination, and trigger buttons for queries/DAGs. |
| **`metadataStructure.ts`** | Interactive SVG DAG visualizing table hierarchy (Snapshot $\to$ Manifest List $\to$ Manifest $\to$ Data Files), click handlers, and inspection cards. |
| **`adHocQuery.ts`** | SQL query editor, Run/Cancel query controls, keyboard shortcuts (`Ctrl+Enter`), execution timer, and query result grid rendering. |
| **`parquetPreview.ts`** | Data preview table with row capping indicators and column headers. |
| **`manifestList.ts`** | Manifest list entries, partition summaries, and added/existing/deleted file counts. |
| **`manifestFile.ts`** | Data file entries, record counts, file sizes, and partition values. |
| **`settings.ts`** | Connection configuration form, credential inputs, validation errors, and connection test buttons. |
| **`connectionDashboard.ts`** | Warehouse overview, namespace list, and instant table name search. |
| **`metadataDetail.ts`** | Searchable, collapsible JSON tree viewer for raw Iceberg metadata files. |

## 4. Inter-Process Communication Bridge (`src/panels/messages.ts`)

Communication between Node.js and Chromium occurs over JSON serialization via VS Code's `postMessage` protocol:

```
Node.js (Extension Host)              Chromium (Webview Sandbox)
       │                                          │
       │       createWebviewPanel(...)            │
       ├─────────────────────────────────────────►│
       │                                          │ (executes inline script)
       │         { type: 'webviewReady' }         │
       │◄─────────────────────────────────────────┤ (initializes listeners)
       │                                          │
       │        PanelMessage (e.g. data)          │
       ├─────────────────────────────────────────►│ (updates DOM)
       │                                          │
       │       WebviewMessage (e.g. action)       │
       │◄─────────────────────────────────────────┤ (user click / input)
```

- **`PanelMessage` (Node.js $\to$ Chromium)**:
  `setState`, `loadMetadata`, `loadManifestList`, `loadManifestFile`, `loadPreview`, `loadQueryResult`, `loadTableOverview`, `loadDataPreview`, `loadConnectionDashboard`, `loadMetadataStructure`.
- **`WebviewMessage` (Chromium $\to$ Node.js)**:
  `webviewReady`, `retry`, `breadcrumbNavigate`, `openManifestList`, `openManifestFile`, `openParquetPreview`, `openAdHocQuery`, `runQuery`, `cancelQuery`, `openTableOverview`, `fetchDataPreview`, `selectStructureSnapshot`.

## 5. Running WebAssembly on Node.js

Node.js runs on the V8 engine, which has native support for WebAssembly (`WebAssembly.instantiate`, `WebAssembly.compile`). In this project, DuckDB is executed in WebAssembly format on Node.js using `@duckdb/duckdb-wasm`.

### Why WASM in Node.js?
Using DuckDB-WASM allows the extension to query Parquet files without requiring native C++ binary bindings (which complicate cross-platform compilation across macOS, Linux, and Windows architectures).

### Execution Details (`src/query/queryEngine.ts`)

1. **Pre-packaging Binaries and Worker Scripts (`package.json`)**:
   During build (`npm run copy-wasm` via `scripts/bundle-duckdb.mjs`), DuckDB assets are prepared in the `out/` directory:
   - `duckdb-eh.wasm` / `duckdb-mvp.wasm` (Compiled WASM binaries, copied directly)
   - `duckdb-node.cjs` (Node-compatible worker runner, bundled with `apache-arrow` inlined)
   - `duckdb-node-eh.worker.cjs` / `duckdb-node-mvp.worker.cjs` (Worker thread entry, bundled with `apache-arrow` inlined)

2. **Isolation via `node:worker_threads`**:
   To prevent SQL execution from blocking Node's main event loop (which would freeze the VS Code UI), DuckDB is spawned in a separate worker thread:
   ```typescript
   import { Worker } from 'node:worker_threads';

   this.rawWorker = new Worker(nodeWorkerScript, {
     workerData: { mod: nodeWorkerMod, name: 'duckdb', type: 'commonjs' },
   });
   ```

3. **Event Adapter Shim**:
   `@duckdb/duckdb-wasm` expects standard browser Web Worker APIs (`addEventListener`, `postMessage`). A shim converts these calls to Node's `EventEmitter` (`rawWorker.on('message', ...)`):
   ```typescript
   const workerShim = {
     addEventListener(type, handler) {
       if (type === 'message') rawWorker.on('message', (data) => handler({ data }));
       else if (type === 'error') rawWorker.on('error', handler);
     },
     postMessage(msg, transfer) {
       rawWorker.postMessage(msg, transfer);
     },
     terminate() {
       void rawWorker.terminate();
     }
   };
   ```

4. **Virtual In-Memory Filesystem**:
   Because WebAssembly runs in a memory sandbox, it cannot directly access the host filesystem by path. The query engine bridges this:
   - Reads Parquet file bytes into a Node.js `Uint8Array`.
   - Registers the buffer as a virtual file in DuckDB: `await db.registerFileBuffer('table.parquet', buffer)`.
   - Runs SQL against the virtual file: `SELECT * FROM 'table.parquet' LIMIT 100`.
   - Unregisters the buffer once queries complete.
